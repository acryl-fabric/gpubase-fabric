# Core–Extension 경계

> 상태: **확정 (2026-10, 주관기관 ㈜아크릴)**. 경계가 애매한 새 기능은 아래 판단 기준으로 정하고, 기준만으로 판단이 안 되면 fabric-acryl이 결정해 이 문서에 추가합니다.
> 근거: 연구개발계획서 p.78~79(Core–Extension 분리 구조를 통한 단계적 상용화 전략), p.108(Core-Extension 분리 구조 기반의 전략적 라이선스 운영)

## 1. 원칙

| 구분 | Core (이 저장소, MPL-2.0) | Extension (JONATHAN GPUBASE, 상용) |
|---|---|---|
| 계획서 정의 | 토폴로지 인식, 제어 인터페이스(라우팅 정책 적용 포함), 기본 트래픽 제어 | 대규모 클러스터 운영, 고급 정책 관리, 통합 시각화, 운영 자동화, 상용 기술 지원 |
| 저장소 | GitHub `acryl-fabric/gpubase-fabric` | 사내 GitLab (비공개) |
| 의존 방향 | Extension을 참조하지 않음 | Core를 Git Submodule로 포함하고 `api/`만 사용 |
| 배포 | Helm 차트 `gpubase-fabric` | Core 위에 별도 차트로 얹음 (§4) |

1. **계획서의 공개 산출물은 모두 Core입니다.** 연차별 "공개 산출물" 목록(p.59~61)에 있는 SW와 문서는 Extension으로 옮길 수 없습니다.
2. **기본 기능은 Core, 차별 요소는 Extension입니다.** 각 기능의 기본 동작(단일 클러스터에서 쓸 수 있는 수준)은 Core에서 완결되고, 대규모·고급·자동화·통합 운영에서 차별이 되는 요소를 Extension으로 둡니다.
3. **의존 방향은 Extension → Core 단방향입니다.** Core 코드, 차트, 문서에 Extension의 패키지 경로, 이미지, 엔드포인트, 설정 키가 나타나면 안 됩니다.
4. **확장점은 `api/`로만 제공하며, 누구나 쓸 수 있는 일반 인터페이스여야 합니다.** Extension 전용 hook, 숨은 플래그, `if enterprise` 같은 분기는 Core에 넣지 않습니다. 확장점은 외부 개발자와 연구기관도 쓸 수 있도록 문서화합니다(p.108 플러그인 구조).
5. **Core만 설치해도 동작해야 합니다.** Extension이 없다고 Core 기능이 빠지거나 성능이 떨어지면 안 됩니다.
6. **환류**: Extension에서 검증된 일반 기능을 Core로 옮길 때(p.108 "공개 SW Core로 환류")는 일반 PR로 올리고, 고객 정보와 Extension 전용 설정을 제거합니다.

### 판단 기준

새 기능이 어느 쪽인지 애매하면 순서대로 확인합니다.

1. 계획서 공개 산출물이거나 그 산출물이 동작하는 데 필요한가? → **Core**
2. 단일 클러스터 운영자가 이 기능 없이 Core를 제대로 쓸 수 없는가? → **Core**
3. 다수 클러스터·다수 테넌트 운영, 정책 자동 최적화, 다계층 통합 분석, JONATHAN GPUBASE 자산(인벤토리, 사용자·과금, UI)과의 결합처럼 상용 차별 요소인가? → **Extension**
4. 그래도 애매하면 fabric-acryl이 결정해 §3에 기록합니다.

## 2. 영역별 경계

| 영역 | Core | Extension |
|---|---|---|
| 대시보드·시각화 | 기본 관제 화면: 패브릭·노드 상태, 토폴로지 뷰, 기본 메트릭, 장치별 트래픽 조회 (`fabric-manager/dashboard`) | 통합 가시화: JONATHAN GPUBASE UI 통합, 다계층(VM/컨테이너↔장치↔플로우) 뷰, 장애 지점·전파 범위 분석 |
| 트래픽 가시화 엔진 | 기본 플로우 수집(sFlow 등 텔레메트리)과 장치 단위 플로우 조회 API·화면 | VM-to-VM 다계층 매핑(GPUBASE 워크로드 정보 결합), 이상 트래픽 탐지, 장기 이력 분석 |
| 자원 격리·QoS | 기본 격리와 QoS 제어: 테넌트·워크로드 단위 RNIC 자원 분리, 최소 보장·최대 제한·우선순위 정책 적용 API | 워크로드 특성 기반 자동 정책 튜닝, SLA 기반 최적화, 다수 클러스터 일괄 정책 관리 |
| 라우팅·혼잡제어·다중경로 | 엔진과 정책 적용 인터페이스 전체 (공개 산출물) | 대규모 정책 템플릿·검증 워크플로 |
| 운영 자동화 | 기능 자체에 필요한 자동 동작: reconcile 루프, 링크 장애 시 경로 재계산, 토폴로지 변화 반영 | 운영 단위 자동화: 업그레이드·점검 오케스트레이션, 런북 자동화, 다수 클러스터 일괄 작업, 용량 계획 |
| 배포 | `deploy/gpubase-fabric` (Core 컴포넌트만) | Extension 전용 차트 (§4) |
| 지원 | GitHub Issues, 커뮤니티 | 상용 기술 지원, SLA |

## 3. 결정 기록

| ID | 쟁점 | 결정 | 근거 |
|---|---|---|---|
| (a) | 1차 "통합 운영 대시보드 프로토타입" vs Extension "통합 시각화" | 기본 관제 화면은 **Core**. 통합 가시화는 Extension | 1차 공개 산출물이므로 Core(원칙 1) |
| (b) | 3차 "오픈소스 플랫폼 통합 배포 패키지" vs Extension "대규모 클러스터 운영" | 배포 패키지에는 **Core만** 포함. Extension은 그 위에 얹는 별도 차트로 배포 (§4) | 상용 기능을 공개 패키지에 넣지 않으면서 업그레이드 경로를 확보 |
| (c) | "데이터 트래픽 가시화 엔진"은 공개 산출물 목록에 없음 | **기본 플로우 수집·조회는 Core**, 다계층 매핑·이상 탐지·장기 분석은 Extension | 기본 가시화는 단일 클러스터 운영에 필요(기준 2). VM-to-VM 매핑은 계획서(p.45)상 GPUBASE 워크로드 정보와 결합하는 기능이라 Extension이 자연스러움(기준 3) |
| (d) | 의존 방향과 확장 방식 | **Extension → Core 단방향 유지**. 연동은 out-of-process(gRPC·CRD)를 기본으로 함 (§5) | 오픈 코어 프로젝트의 일반적인 방식이며, 이 과제의 이원화 저장소·라이선스 구조와 맞음 |
| (e) | QoS 제어 엔진 소스코드는 공개 목록에 없음(1차 설계서, 3차 검증 보고서만 공개) | **기본 격리·QoS 제어는 Core로 공개**. 자동 정책 튜닝 등 차별 요소는 Extension | 기본 기능은 공개, 차별 요소는 Extension(원칙 2). 3차 QoS 검증 보고서를 재현할 수 있어야 함 |
| (f) | p.79는 Extension에 "운영 자동화"를 포함, p.108은 미포함 | **p.79 기준으로 운영 자동화를 Extension 범위에 포함**하되, 기능 자체의 자동 동작은 Core로 구분 (§2) | 적응형 라우팅·토폴로지 반영 같은 자동 동작은 공개 산출물의 핵심이라 Core여야 함. 운영 단위(fleet) 자동화만 상용 차별 요소로 봄 |

## 4. 배포 구조 (b)

```text
helm install gpubase-fabric  oci://ghcr.io/acryl-fabric/charts/gpubase-fabric     ← Core (공개)
helm install gpubase-ext     <사내 레지스트리>/jonathan-gpubase-fabric-ext          ← Extension (상용, 별도 릴리스)
```

- Extension은 Core 차트를 수정하거나 재패키징하지 않고, **같은 클러스터에 별도 릴리스로 얹습니다.** Core를 먼저 설치하고, Extension을 추가하거나 제거해도 Core 릴리스는 바뀌지 않습니다.
- 이를 위해 Core가 지켜야 할 것은 다음과 같습니다.
  - Service 이름, 포트, CRD를 안정된 계약으로 유지합니다(`api/` 버전 정책 적용, NAMING.md 라벨로 찾을 수 있음).
  - CRD는 Core 차트가 설치하고 소유합니다. Extension은 자기 CRD를 별도 API 그룹으로 정의합니다.
  - 플러그인 등록은 `api/`의 out-of-process 방식(gRPC 엔드포인트 등록)으로 열어 둡니다. 구체 방식은 1차년도 인터페이스 정의 때 확정합니다.
- 버전 호환은 [JONATHAN GPUBASE 연계 가이드](../guides/jonathan-gpubase-integration.md)의 호환 표로 관리합니다.

## 5. 의존 방향과 연동 방식 (d)

**다른 오픈 코어 프로젝트의 방식**

| 방식 | 예 | 특징 |
|---|---|---|
| 같은 저장소 안에 상용 디렉터리(`ee/`)와 별도 라이선스 | GitLab, (과거) Elastic X-Pack | 개발은 편하지만 공개 저장소에 상용 코드가 함께 있어 경계가 흐려짐 |
| 별도 저장소의 상용 빌드가 OSS를 라이브러리로 가져와 hook 구현 | Grafana Enterprise, Mattermost | 의존은 상용 → OSS 단방향. OSS에 hook 인터페이스가 필요하고, 같은 바이너리로 빌드됨 |
| 별도 컴포넌트·서비스로 OSS API에 붙음 | Kubernetes 생태계(오퍼레이터, CRD), Kong 플러그인 | 의존은 단방향. 프로세스와 릴리스가 분리되어 버전 독립성이 높음 |

**이 과제에 적용하는 방식**

- 의존 방향은 **Extension → Core 단방향**을 유지합니다. 세 방식 모두 이 방향이 공통이고, Core 단독 동작, 외부 기여, 라이선스 분리를 지키는 전제입니다.
- 연동은 **out-of-process(gRPC·CRD·별도 차트)를 기본**으로 합니다.
  - 계획서가 Kubernetes·SONiC 표준 인터페이스를 전제하고 있고, 컴포넌트가 여러 언어라서 빌드 시점 링크보다 API 연동이 맞습니다.
  - Core와 Extension의 릴리스 주기를 분리할 수 있습니다. 공개 Core는 연차별로, 상용은 고객 일정에 맞춰 릴리스합니다.
  - MPL-2.0은 파일 단위 copyleft라 Go 라이브러리로 가져와도 Extension 파일은 비공개로 둘 수 있습니다. 그래도 프로세스를 분리하면 경계가 코드 리뷰 없이도 명확해집니다.
- **in-process Go 플러그인**(`api/plugin/v1alpha1`)은 지연에 민감한 경로(예: 경로 계산 정책)처럼 프로세스 분리가 맞지 않는 경우에만 씁니다. 이때도 Core는 인터페이스만 정의하고 구현은 Extension 쪽에 있습니다.
- 주의할 점: Extension만을 위한 확장점을 Core에 만들지 않습니다(원칙 4). 확장점은 외부 개발자도 쓸 수 있는 일반 인터페이스로 설계하고 문서화합니다.

## 6. 리뷰 체크리스트

PR 리뷰에서 다음 중 하나라도 해당하면 경계 위반으로 봅니다.

- Extension, 사내 GitLab, 고객사 환경을 가리키는 import, URL, 이미지, 설정 키
- §2 표의 Extension 열에 해당하는 기능의 구현 또는 상세 설계
- `api/`를 거치지 않는 Extension 전용 분기, 특정 상용 제품만을 위한 hook
- 고객 데이터, 고객사 이름, 내부 운영 수치
- 계획서 공개 산출물을 Core에서 빼거나 기능을 줄이는 변경
